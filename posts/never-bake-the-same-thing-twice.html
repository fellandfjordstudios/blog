Never bake the same thing twice

Every change to my asset library made the daily build bake everything again. I changed the cache to key each bake on what it actually reads; in a cloud development container, a full catalog rerun went from 2,199 s to 206 s. Those are single-run measurements, with some overlap from other work during the first run, rather than a controlled benchmark.

Every commit rebuilt everything

A bake is the expensive step that turns an asset’s built shape into the files a game loads: meshes, lighting data, and distant-view images called atlases. Building the shape itself is cheap. Baking and rendering the results is where the time goes.

My daily build ran on a stateless CI runner. It saved its bake output between runs, but the cache key named the whole asset library’s commit. Any new commit meant a new key. Even changing a comment threw away the saved work and sent every asset through baking and rendering again.

The bakes had a 45-minute budget. Whatever didn’t finish shipped unbaked. That made the choice of cache key visible in the result: time spent repeating finished work was time unavailable for something that still needed baking.

On 14 October 2026, I measured the gap between the commit the daily build was pinned to and the library’s main that day. Across 164 commits, none of the catalog’s 167 baked levels of detail had changed in the shape the build actually made. Rebuilding that set would have produced the same thing.

The commit was useful for identifying the library version. It was much less useful for deciding whether a particular bake needed doing. I needed a key that could tell those questions apart.

Two keys that fail in opposite directions

The obvious place to start was the asset’s own recipe. If that hadn’t changed, perhaps its bake could stay. But an asset also depends on shared library code. A key that ignores that code can miss changes which affect the finished shape.

Across the same 164 commits and 167 LODs, none of the recipe-only keys moved. That result looked reassuring until I considered what the key could see. It would have kept serving the old bakes through all that library work, whether or not the work changed what the bake needed.

Including the shared code each asset reaches fixed the blindness. It also moved every key. That was safe, but left me with the full rebake I already had.

The built-shape key gave the same count as the blind key, but for a reason I could trust: I had built the shapes and compared what came out. The code had changed; the output the bake would read had not.

That was the useful boundary. The cheap step could absorb changes to the code and tell me whether the expensive step had anything new to do.

Key the bake on what it reads

I now key the bake on the shape as built, plus whatever reaches the bake without passing through that shape: the material as declared, the baking code itself, quality settings, and the engine version. There is also a version number for the key format.

That last part lets me change how the key is assembled without confusing old entries with new ones. Changing the baking code moves every key once, as it should. Changing library code only needs to move a shape’s key when it changes the shape the build makes.

There is a price for knowing. Building all 167 LODs just to compute their bake keys took 61 s in the cloud development container. A cache lookup isn’t free when I first have to make the thing I’m identifying. I was happy to spend about a minute finding out what needed baking instead of assuming everything did.

The local store lives outside any checkout, with each bake stored under its key. I write into a temporary folder and rename it into place when complete, so an interrupted bake leaves no half-written entry. Before reusing an entry, I check every file against its recorded hash.

What it saved

I measured an empty store, then immediately ran the same work again with nothing changed. These were single runs in a cloud development container. They are not daily-runner timings, phone or player timings, averages, or a cache hit rate.

The full catalog run covered 132 assets and 408 LODs, with structural baking and no lighting trace. The rerun read all 408 LODs from the store and wrote a manifest byte for byte identical to the first. Computing the keys took about 150 s of its 206 s.

The packaging tool covered 167 LODs, also with structural baking. Its unchanged rerun read all 167 from the store; the remaining work was computing keys. I didn’t measure the slower lighting-trace mode, which takes hours on that machine. It reads the same keys.

The goods sack’s atlas was also byte for byte the same either way. The remaining time went into starting the engine, importing, and building the shape to compute the key.

Computing the catalog’s 167 bake keys and 103 render keys alone took 3 min 5 s, single-threaded in that container. Once the bakes were cached, most of what remained was working out what I already had.

The daily build now restores its bake store from the previous run whatever commit it builds. I haven’t measured its runtime, so these container results are the timings I can report.

Sharing it between machines

A local store helps the machine holding it. The next step is a shared store, written by verified builds and read by everyone, using a Cloudflare Worker in front of R2 storage. Parts of that are now in use, but the transfer work isn’t finished.

First I had to make a key mean the same bytes across machines. Randomly assigned internal IDs in saved scenes meant that 400 of 400 entries differed under the same keys when baked on different machines. The later writer silently replaced the earlier result.

The rule now is that a key must produce the same bytes on any machine. The first verified writer wins. If another writer supplies different bytes, the store records a disagreement and keeps the original entry.

Fetching each result separately was also too expensive. In a tiny HTTP-cache test with one asset and three LODs, fetching took 3.26 s against 2.37 s for baking from scratch. About 2.26 s of the cached run was building shapes to learn their keys. That test wasn’t a reason to add more individual requests.

Instead, a build publishes a “root”: a list of every key it needs. A client compares that with what it already holds and moves the difference in batches. On Cloudflare’s free tier, my cold-transfer target is at most 2x the time needed to move the same bytes as a single file.

The first real attempt used batches of 1,000. Each took about 35 s and about 350 ms of Cloudflare CPU; Cloudflare stopped the sixth batch for exceeding the free tier’s CPU allowance. Recording each batch’s ownership in a single D1 database write, instead of a storage object per entry, removed that problem. Sending batches several at a time helped further.

The cold transfers met the target. The small, mostly-held syncs didn’t: a few fixed calls dominate when there is little to move.

The first reads through the deployed Worker failed altogether, with HTTP 403. Cloudflare’s browser integrity check refused Python urllib’s default User-Agent with error code 1010 before the requests reached the Worker. Naming the client fixed it. During that failure I got no cache hits; I never got wrong bytes.

Where I ended up

The local cache is in use, and the library’s build now fetches through the shared Worker on the free tier, with no charge. Getting mostly-held syncs within the transfer target is next.

The change I would carry to another pipeline is to key the expensive stage on the cheap stage’s output, together with the other inputs it reads. It costs time to build that output. Here, that cost let me keep finished work through library changes that didn’t affect it.

You can browse the results in the asset catalog, or play Transect in the browser. I’ll keep working on moving less of the same data around to build them.
