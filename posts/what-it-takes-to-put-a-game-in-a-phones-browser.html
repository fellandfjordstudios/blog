What it takes to put a game in a phone's browser

Transect is a walk through a valley that doesn't exist. You open a link on your phone, and a minute later you're standing on a trail in a Scottish-looking glen, with the light changing and rain coming in after dark. No app store and no install. That last part turned out to be the hardest thing we've done.

Sixty-four megabytes

We gave ourselves a budget: the whole game in 64 MB, about what a phone will download on a patchy connection without the player giving up. The game engine alone, Godot compiled for the web, takes 36 MB of that before a single tree exists. Everything else, the valley, the sky, the sounds and the code, has to fit in what's left. Today the game is 58 MB. Every new feature is a negotiation with that number.

The phone decides the frame rate

On a desktop you can throw geometry at the screen. On a phone, the limit is how many separate things you ask the graphics chip to draw each frame. We measured it on an iPhone. It held about 290 draw calls at full speed, and nothing we tested held more. So that became a hard cap, and every scene is judged against it, not against how it looks on a laptop.

Memory is the other wall. A phone browser will quietly kill a tab that uses too much, with no error, just a reload. Our walk peaks around 1.3 to 1.5 GB, which is close to where phones start doing that. We measure it on every build now.

Threads that browsers won't give you

Browsers only allow a web page to use multiple CPU threads if the page is served with special isolation headers. Many hosts don't let you set them. So we ship the engine twice: a single-threaded version that runs anywhere, and a threaded one the page picks only when the browser allows it.

The first time costs the most

The first time the game draws a new kind of surface, the browser has to compile a small program for the graphics chip. We counted 31 of them in the valley, and 16 were being compiled twice. Each one is a stutter, and in the cave we measured pauses of nearly eight seconds. The fix is to do that work on the loading screen, where a wait is expected, instead of mid-step on the trail.

Getting it onto the web at all

Even publishing was a fight. Our first release, about 46 MB pushed in one piece, was simply refused by the host. Now every release goes up in pieces of 20 MB or less, and the live page only switches once the whole thing has arrived. No player ever loads half a game.

Tests that pass, and a game that doesn't work

The lesson that changed how we work came from Norge, the game we're building next. It passed every automated test we had. Then we opened it in a browser as a stranger would and pressed Cast off. The boat said it was under way, and nothing ever happened. Every test had been checking the rules directly. None had played the game.

Now nothing counts as done until a person can do it in the built game, in a browser, and say what they saw. “The code handles it” isn't the bar. “I cast off and watched the shore get smaller” is.
